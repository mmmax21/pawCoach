## 做了什么

写 `pawcoach/coach/rules.py`：确定性、可测试、纯 Python 的进度规则层，输出 `ProgressPlan`（下一次训练的目标时长 + 动作 + 重点 + 频率）。

四条规则（照 CodePlan_detail.md C2）：

| 规则 | 实现 |
|---|---|
| 最近 2 次成功率 ≥ 80% → 目标时长 +20～30% | 升档，`target × 1.25`（取中值 25%），`action="increase"` |
| 成功率 < 50% → 回退上一档 | 回退，`target × 0.8`（÷1.25 对称步长），`action="decrease"` |
| reward_delay > 1.0s 占比 > 30% → 重点改「标记时机」，时长不加 | `focus="标记时机"`，且只拦升档、不拦回退 |
| 频率/时长 3～5 分钟、5～10 轮 | 常量 `SESSION_RECOMMENDATION`（Demant 2011） |

优先级：回退 > 升档 > 保持（成功率低是硬信号）；规则 3 只把 `increase` 改成 `hold`，不覆盖 `decrease`。

## 设计决策（两个原文没写死的地方，我做了明确取舍）

1. **「回退上一档」实现成「÷1.25（-20%）」**，而不是引入一个离散档位表。原文「+20～30%」（连续）和「上一档」（离散）混用了两种说法；若档位按 +25% 等比递增，上一档 = 当前 ÷1.25，自洽且不引入原文没有的档位序列。升档用中值 25%（20～30% 区间内）。**如果宵本意是要一个离散档位表（如 3s→10s→加干扰），这里要改。**
2. **`target_hold` 是必需参数**（当前目标保持时长），规则层不猜它从哪来。但 `schema.py` 里目前没有「目标时长」字段——C3 接 coach 时必须先解决「当前目标从哪来」：要么 `meta.json` 加字段，要么从 history 上次的目标推断，要么用本次 median_hold 对齐。这是 C3 的前置决策，C2 只把纯函数写好。

## 基线（只记，不设门槛）

规则层的阈值（80% / 50% / +25% / 1.0s / 30%）**全部照原文取，没有真实多日训练数据可验证**——本仓库没有同一只狗连续多天的记录（B 阶段已知问题）。所以「规则准不准」这条基线没得算，C2 只保证「规则实现可测、边界清楚」。真要验证得等拿到同犬多日数据，或 C5 的 30 用例评估里用合成数据走一遍。

## 遗留

1. `target_hold` 来源未定（见上），C3 接 coach 前要定。
2. 规则层还没接进 coach，C3 才把 `ProgressPlan` 注入 `LLMCoach` 的 prompt。
3. 阈值全是原文抄的，没有实证依据，真上线前要对着真实训练数据校一遍。
