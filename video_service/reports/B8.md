# B8 奖励合并（tap > marker > visual）+ 跑通 + 记基线

- 预计工时：1～1.5h
- 验收命令：
  ```bash
  PYTHONPATH=. .venv-b/bin/python -m pawcoach.cli analyze data/raw/dog3.mp4 -o results/dog3.json
  # 期望：trials[].reward_t 与 meta.reward_taps 对齐；没打点的轮次由 marker 兜底；reward_delay 可算
  ```
- 验收结果：**通过**
  - 写 `pawcoach/reward/merged.py` 的 `MergedRewardExtractor`：优先级 **tap > marker > visual**。
    - tap：读 `meta.reward_taps`，每个转成 `RewardEvent(source="tap")`；
    - marker：对每个 marker 事件，若附近 2s 窗口内没有 tap，说明该轮没打点，用 marker 时刻兜底 `source="marker"`；
    - visual（MediaPipe Hands 判「手伸向狗头」）按计划只做可选增强，本版不做——失败不影响任何东西。
  - `analyze` 里 `TapRewardExtractor` 换成 `MergedRewardExtractor`（只改 `cli.py` 的 import + 调用两处，编排 / align 不动）。
  - **marker 兜底覆盖判断只按 tap**，不看成累积的 marker reward——否则相邻两个 marker 会互相「覆盖」，漏掉第二个兜底（这是实现里踩过并修掉的一个 bug）。
  - 单测 `tests/test_merged.py` 5 个用例：tap 直接透传、无 tap 时 marker 兜底、窗口内 tap 覆盖 marker、窗口外 marker 兜底、按时间排序。全量回归 **45 passed**（原 40 + 新增 5）。
  - dog3 干净重跑（`.venv-b` 真姿态 + 真口令）：`reward_taps=[]`、marker 词 `yes`，asr 缓存里有 3 个 `Yes.`（13.0/27.0/39.0）→ 走 marker 兜底，出 3 个 `source="marker"` 奖励，`success_rate = 1.0`（之前 `TapRewardExtractor` 只读 `reward_taps`，空打点时 `success_rate = 0.0`）。

## 基线（只记，不设门槛）

没有干净的「口令、坐下、保持、释放、递零食」完整训练样本（dog3 带字幕和训练师讲解），也没有 `reward_taps` 真值，所以「打点对齐误差（用户打点 vs 实际递零食时刻）」这项基线没得算。只记录 dog3 的实际产出：

| 轮次 | cue_t | sit_start | sit_end | reward_t | reward_delay | source |
|---|---|---|---|---|---|---|
| 1 | 0.0 | 1.83 | 7.47 | 13.0 | 11.17 | marker |
| 2 | 11.0 | 11.80 | 20.20 | 13.0 | 0.0 | marker |
| 3 | 26.0 | 26.97 | 33.83 | 27.0 | 0.0 | marker |
| 4 | 37.0 | 39.10 | 50.47 | 39.0 | 0.0 | marker |

`MergedRewardExtractor` 本身产出 3 个奖励：`marker 13.0 / 27.0 / 39.0`（轻量验证直接打印确认）。

## 遗留问题

1. **跨轮奖励归因是粗糙的**（`align.py` 的 `next(r for r in rewards if r.t >= sit_start)`，reward 不被消费）：第 1 轮和第 2 轮都指向同一个 `reward_t=13.0`，第 1 轮 `reward_delay=11.17s` 明显是错的。这是 C 阶段迭代项（正确切分、跨轮归因），B8 只记录基线不修。
2. 没有真实干净样本 + 没有 `reward_taps` 真值，「打点对齐误差」基线要到 D 阶段或拿到自拍视频再补。
3. visual 分支（手伸向狗头）未实现，按计划是可选增强，不影响链路。
