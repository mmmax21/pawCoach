# 交接：实时计时（边拍边显示口令、坐下、奖励和奖励延迟）

| 项目 | 内容 |
|---|---|
| 来源 | 用户在 2026-11-20 要求"边拍边显示"，并选定实时口径（不是录完回放） |
| 实现 | Opus 5.5 |
| 状态 | 服务端和手机端代码完成，自动测试通过，**没有在真手机上跑过** |
| 关系 | 与 `2026-11-19-video-correction-v2.md`（取景自检 + 录完统一看）并存，互不替代 |

## 一、做了什么

录制过程中，屏幕实时显示：狗是坐着还是站着、口令什么时候出声、狗什么时候坐下、奖励什么时候出现，
以及奖励比坐下晚了多久。狗坐下后读数从 0 开始走，奖励一出现就定格；超过内容库阈值变红，
并在读数下方显示内容库里"奖励给得太晚"那一条 `common_mistakes` 的原文。

不改离线上传路径。离线路径对口令的识别依赖 Whisper 转写，实拍里不稳定（交接单 M5 有记录）；
实时路径换了测量方式，见下。

## 二、为什么能做到实时，和离线路径的三处不同

| | 离线（M5） | 实时（本次） |
|---|---|---|
| 口令、奖励时刻 | Whisper 转写出词，再按词表匹配 | **只认"有没有出声"的时刻**，不识别说了什么 |
| 区分口令还是奖励 | 看转写出的词是不是口令词 | 看出声时狗当时在做什么：坐下前是口令，坐下后第一声是奖励 |
| 奖励的另一来源 | 标记词 | 屏幕上的"奖励"按钮点按，优先于声音，不依赖麦克风 |
| 姿态平滑 | 0.5 秒窗口多数投票（要看未来的帧） | 滞回确认（只看已到的帧），确认后把切换时刻倒推回最早那一帧 |
| 速度 | 24 秒视频分析 43–59 秒 | 一帧约 20–30 毫秒，5 帧每秒，延迟读数不依赖整段分析 |

起音检测的取舍：不认词意味着周围有别人说话、电视、狗叫都会被当成"有人出声"。
冷启动前 0.5 秒只学底噪，所以点开始后请先安静半秒。

**一段真实视频**（`宠物狗训练模拟1.mp4`，侧拍、英文口令）：姿态正确识别出四次坐下

**不能当作准确率证据**：它没有"每次口令后立刻奖励"的清晰结构。见下"没验证的"。

## 四、没验证的（上真机前必须知道）

1. **没有在任何真手机上跑过。** 相机图像流 + `record` 插件同时占用麦克风，会不会冲突没有测。
   Android 常见的情况是相机预览与麦克风采集可以并存，但这一点没有证据。
2. **没有真狗视频的准确率。** 姿态在一段真实侧拍上对，但起音 / 轮次推导只在合成视频上有已知答案。
   真实环境里"口令之后的第一声"不一定是奖励，主人可能说话。
3. **俯拍不支持。** 姿态判据是侧面几何（见 v2 方案第一节），俯拍会判成"看不清"，页面显示"狗：还没看清"。
4. **局域网延迟没测。** 回环延迟约 0.4–0.6 秒；Wi-Fi 上每帧 320×180 RGB 约 170 KB，5 帧每秒约 0.85 MB/秒，
   正常家用 Wi-Fi 够用，但没有实测。
5. **一个起音检测的已知弱点**：响片的"咔"只有二三十毫秒，达不到最少 3 帧（60 毫秒）的门槛，不会被识别为出声。
   要用响片请点屏幕上的"奖励"按钮。
6. **练习中切后台**：相机和连接会被系统收走，页面会直接结束这一次并把已有结果交回，不尝试无缝继续。
7. **姿态确认要 0.6 秒**：狗坐下后读数要等 0.6 秒才开始走，但起点已倒推到真正坐下的那一帧，所以数字本身不偏。

## 六、几条值得记住的设计决定

- **阈值读内容库，不写死。** 页面从 `video_checks.yaml` 的 `late_reward.threshold_sec` 取"晚"的界线，
  通过 WebSocket 的 `start` 消息传给服务端。内容库没有这条配置时入口不显示。
- **服务端只发提示代码，不发文字。** `reward_due` / `reward_late` / `cue_repeated`，文字在手机端 `LiveStrings`，
  训练方法的话一律来自内容库 `common_mistakes` 原文。原文性测试检查页面上每一段文字不是模板就是内容库原文。
- **口令和奖励靠"当时狗在做什么"区分**，不靠听词。坐下前的出声是口令（出现几次就是几次口令，口令重复就是这么数的）；
  坐下后第一声是奖励，之后是保持期间的标记词。
- **响片在屁股碰地的瞬间按下是正确做法**，不能因为它紧贴着坐下就被当成"第二次口令"。
  容差只有 0.1 秒，用来吸收 5 帧每秒带来的取整误差，不能再大。
- **时间用手机自己的会话时钟。** 服务端不用自己的时钟，网络延迟只会让数字晚一点出现，不会让"奖励延迟"变大。
- **提示优先级**：已经坐下还没奖励（正在发生）高于口令重复（已成事实）；口令次数始终显示在轮次行里，不会因让位而丢失。

## 七、开发中发现并修掉的问题（供复盘）

| 问题 | 原因 | 处理 |
|---|---|---|
| 同样的坐姿，第一次认得出、第二次整段"看不清" | 判坐只用脖根和尾根两个点，一个点置信度略低于 0.3 整帧就作废；离线靠窗口投票兜住，实时没有 | 某个点不可靠时用相邻点顶替；dog3 单帧 38/50 → 42/50，合成视频坐姿漏判 5–7 帧 → 0 |
| 坐下后立刻奖励被算成"口令重复、奖励晚" | 坐下前的容差放得太宽（0.25 秒），把紧贴坐下的正确奖励吞成了第二次口令 | 容差收到 0.1 秒，补回归测试 |
| 第二次坐下被倒推并进第一次 | 倒推时穿过了两次之间"看不清"的站姿 | 倒推不得越过上一段结束时刻 |
| 狗出画后坐姿一直不结束 | 画面边缘的杂帧刷新了超时计时 | 改为按"上一次真正看到当前状态"计时 |
| 没有口令的坐下把里面的声音留给下一轮当口令 | 被跳过的坐下没有推进"已过去的时间" | 跳过时同样推进 |
| WebSocket 地址会带上原地址的查询串 | `Uri.replace(query: null)` 是"不改"不是"清空" | 用构造函数重新拼 |
| 屏幕上的"奖励晚了"可能在服务端确认前提前亮红 | 本地补算读数用了本地时钟 | 已奖励的轮次以服务端判定为准 |

## 八、如何运行

```bash
# 服务端（pawcoach 环境，video_service/ 下）
PYTHONPATH=. uvicorn app.main:app --host 0.0.0.0 --port 8001

# 不接手机：用视频当手机，按真实速度推流并量屏幕延迟
PYTHONPATH=. python scripts/live_ws_client.py <视频> --url ws://127.0.0.1:8001/live

# 手机端：打开视频功能，技能页（坐下）出现"实时计时"
cd app && flutter run --dart-define=VIDEO_ANALYSIS=true --dart-define=VIDEO_BASE_URL=http://<电脑IP>:8001
```

入口只出现在有 `late_reward` 检测的技能（目前是 `sit`），且需要 `VIDEO_ANALYSIS=true`。

## 九、演示当天

1. 电脑启动服务后访问 `GET /`，确认 `pose` 为 `ready`；首次连接 `/live` 会预热模型，约 6 秒。
2. 手机和电脑连同一个 Wi-Fi，"我的 → 服务器地址"只管同步和在线教练，**视频服务地址是构建参数 `VIDEO_BASE_URL`**，
   换了 Wi-Fi 需要重新打包。
3. 摆位：手机竖放靠稳，狗侧身，主人在旁。点开始后先安静半秒。
4. 兜底：手机相机出问题时，用 `scripts/live_ws_client.py` 在电脑上推流，大屏显示的是同一份服务端快照。
5. 演示脚本：故意在狗坐下后等 2 秒再奖励，让红色提示和内容库原文出现；再做一次坐下立刻奖励，读数定格为绿色。
