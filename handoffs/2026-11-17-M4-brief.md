## 5. 家庭共享与同步

### 5.1 账号

- **不做短信 / 邮箱验证。** 首次启动时客户端调用 `POST /v1/users` 注册匿名账号，服务端返回 `user_id` 与随机 `token`。之后所有请求带 `Authorization: Bearer <token>`。
- 昵称：建档或加入家庭时填写一次，可在家庭成员页改。`User.phone_or_email` 本期为空。
- token 存本地数据库，不同步。卸载重装等于新账号，这是首版可接受的代价，交接单"已知问题"写明。
- 离线首次启动：先按本地流程建档，联网后再注册并上传。不能因为没网卡住建档。

### 5.2 创建与加入

- 建档完成（或老用户升级后首次联网）：注册账号 → `POST /v1/households` 上传家庭、狗及全部现有数据 → 拿到邀请码。
- 加入：建档第一屏新增"加入已有家庭"入口 → 输入邀请码与昵称 → `POST /v1/households/join` → 全量拉取该家庭数据 → 直接进首页，**不走狗的建档**。
- 已有自己狗数据的设备不能加入别的家庭（首版一户一狗）。入口只在尚未建档时出现。
- 邀请码 6 位，字母数字去掉易混字符（0/O、1/I/L），不区分大小写。重新生成后旧码立即失效。

### 5.3 同步协议

修订 `docs/data-model.md` 的"同步策略"，以本节为准：

- **同步的表**：households、household_members、users（只同步 id 与昵称）、dogs、dog_concerns、dog_cues、weekly_plans、plan_goals、daily_mini_tasks、training_sessions、weekly_reports、ai_conversations、ai_messages、diagnosis_results、care_reminders、dog_badges。
- **不同步的表**：内容库缓存各表、onboarding_drafts、reminder_settings（每台设备各自的每日提醒）、streaks、dog_skill_statuses、同步状态表。
- **Streak 与 DogSkillStatus 不再由服务端重算**，改为每台客户端从同步来的 training_sessions 本地重算。输入相同则结果相同，服务端不需要懂训练规则。
- 每条同步记录带 `client_updated_at`（ISO 8601 UTC，毫秒）和 `deleted`（软删除，默认 false）。服务端额外记 `server_seq`（自增），下行按 `server_seq` 增量拉，不按时间戳，避免设备时钟不准导致漏拉。
- 上行 `POST /v1/sync/push`：一批记录（表名 + 主键 + 字段 + client_updated_at + deleted）。服务端逐条比较，`client_updated_at` 较新者胜，相同时以先到者为准。返回每条是否被采纳。
- 下行 `GET /v1/sync/pull?since_seq=N`：返回该家庭 `server_seq > N` 的全部记录与新的最大 seq。客户端应用时同样按 `client_updated_at` 比较，不覆盖本地更新的记录。
- **确定性主键**：同一事实在两台设备上可能被各自生成。以下记录的主键必须由内容决定，而不是随机 UUID，使两边生成的是同一条：
  - `WeeklyPlan.id` = 由 `dog_id + week_start` 派生
  - `PlanGoal` 主键 = `plan_id + skill_id`
  - `DailyMiniTask` 主键 = `plan_id`
  - `WeeklyReport.id` = 由 `plan_id` 派生
  - `DogBadge` 主键 = `dog_id + badge_id`
  - `CareReminder.id` = 由 `dog_id + template_id + 序号` 派生（用户手动新增的除外）
  派生方式自定，写进交接单；要求稳定、跨设备一致。
- **徽章例外**：`DogBadge` 一旦存在不被覆盖（服务端对已存在的 dog_badges 拒绝更新），保证 `earned_at` 与 `earned_by_user_id` 是第一个获得者。
- 节奏：本地写入后立即触发一次推送（失败排队重试）；App 在前台时每 5 秒拉一次；从后台回到前台立即拉一次。后台不轮询。
- 拉到新的 training_sessions 后，重算 Streak、DogSkillStatus、徽章，并刷新首页，**不需要用户手动刷新**。

### 5.4 服务端存储

- sqlite3 单文件，路径来自环境变量 `DB_PATH`，默认 `server/data/app.db`，目录加入说明不入库。
- 一张通用记录表即可：`(household_id, table_name, pk, payload_json, client_updated_at, deleted, server_seq)`，主键 `(household_id, table_name, pk)`。服务端不解析训练字段。
- 另有 users、households、tokens、invite_codes 几张小表。
- 每个请求校验 token 对应用户属于该家庭，不属于返回 403。

### 5.5 视频备注

本期**不上传视频文件**。其他成员看到带视频备注的记录时，显示"视频保存在录制者的手机上"，不报错。

## 7. 徽章（ST-2）

- 定义全部来自 `content/badges.yaml`，`domain/badges.dart` 按 `condition_type` 判定，纯函数。输入：训练记录、Streak、掌握技能数、诊断结果、家庭成员及其打卡记录。
- 判定时机：每次打卡后、技能状态变化后、诊断完成后、成员加入后、每次下行同步后。
- `household_members`（全家总动员）：家庭里**至少 2 位成员各自有过打卡记录**才颁发，与 yaml 中 description 一致。
- 新获得徽章时弹一次祝贺（名称 + description 原文），同一徽章在同一设备只弹一次。其他成员下次打开时也弹一次，文案写明是谁获得的。
- 徽章墙：已获得的彩色显示获得日期与获得者，未获得的灰色显示 description 作为获得条件。
- 图标：按 `condition_type` 映射 Material 图标，yaml 里的 `icon` 字段本期不用，交接单注明。

## 8. 疫苗 / 驱虫日历（CR-1）

- `domain/care_calendar.dart` 输入出生日期与 `care_calendar.yaml`，输出 CareReminder 列表，纯函数：
  - 一次性项：due 日期取 `week_from` 与 `week_to` 的中点周（向下取整）对应的日期。
  - 重复项：从 `week_from` 起每 `every_weeks` 周一次，直到不超过 `week_to`。
  - `milestones` 不生成提醒，只在养护页时间线上作为信息条展示。
- 生成时机：建档完成时；M4 升级后老用户首次启动时；修改出生日期时（只重算 `source = default` 且未完成、未跳过的条目，用户改过日期的条目视为 `source = user`，不动）。
- 已过期的一次性条目照常生成，进入"待确认"分组，主人可标"已完成"或"跳过"，**不为过期条目推送**。
- 养护页：顶部固定展示 yaml 的 `disclaimer` 原文；按"待确认 / 即将到期 / 以后 / 已完成"分组；可改日期、标记完成、跳过、手动新增一条。
- 推送：到期日当天 09:00 本地通知，标题用条目 `title`，正文用条目 `note` 原文。只预排未来 60 天内的条目（Android 待发闹钟有数量上限），启动、编辑、同步后整体重排。通知 ID 用独立区间（如 2000–2999），不得与每日提醒的 1001–1014 冲突。
- 所有条目全家同步，每台设备各自预排推送。

## 9. M3 决策落实

**第 8 条：前置未满足时加入其前置（演示关键）**

对诊断方案中的每个技能 S：
1. 已掌握 → 跳过，原因"已掌握"。
2. 已在本周目标 → 跳过，原因"已在计划中"。
3. 前置已全部掌握且周龄满足 → 加入 S。
4. 否则沿技能树向上，找出 S 的前置链上**当前可练**的技能 P（周龄满足、未掌握、其自身前置已全部掌握）加入，可能不止一个。弹窗写"先练 P，为 S 打基础"。P 若已在目标中或已被本次加入，不重复。
5. 若 S 本身周龄未到且前置链上也没有可练的 → 跳过，原因"X 周龄后再练"。

加入的技能 `source = ai_diagnosis`，受本周上限 6 约束，超出部分按方案顺序截断并在弹窗说明。"加入下周"用同一规则，只是周龄按下周一计算。纯函数实现在 `plan_generator.dart`，弹窗文案的技能名取内容库。

**第 2 条**：并入上面第 1 步，本周、下周一致。

**第 5 条**：`nextWeekPlan()` 的目标总数上限 6，优先级诊断技能 > downgrade > carryover > 其余。

**用例必须覆盖**（2026-11-17 修订，原"至少新增 1 个技能"作废）：10 周龄、什么都没掌握的狗做"扑人"诊断后点"加入本周"：
- 新增的技能都必须是当前可练的；**不允许为了"有新增"而加入任何不可练或与方案无关的技能**。
- 若方案的基础技能已全部在本周计划中（10/15/30 分钟档的实际情况），弹窗不能只显示"已跳过"，必须写明：哪些已在计划中的目标正是在为方案打基础（"本周计划里的 P1、P2 正是在为 S 打基础，先把它们练好"），以及方案技能的解锁条件（"S：掌握 P1、P2 后解锁"）。技能名取内容库。
- 5 分钟档的同一只狗应新增 lure_follow。
- 不新增 PlanGoal 字段，不改首页标签逻辑。

**修订理由**：10 周龄的狗能练的基础技能，默认计划本来就已经排了，这是周计划生成器在正确工作。诊断此时该做的是告诉主人"你现在练的就是在解决这个问题"，而不是塞进新技能。

**演示建议**：演示用狗可另备一只约 14 周龄、已掌握叫名回应与跟随诱导的档案，诊断"扑人"会直接加入坐下等技能，展示效果更完整。

5. **双端可见性（验收口径第 5 条）**：写一个可自动执行的端到端测试——起真实 `server/`，设备 A 跑集成测试打卡，另一进程以成员 B 的身份轮询 pull，记录从 A 打卡到 B 拉到该记录的耗时；反方向同样测一次（B 用 API 推一条训练记录，A 的首页在 10 秒内显示）。两个方向都要 ≤10 秒。
6. M3 → M4 迁移：带 M3 数据的数据库升级后数据完整，现有记录都有 `client_updated_at`。
7. 既有测试全部不回退。
