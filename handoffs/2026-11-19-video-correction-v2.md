# 方案：视频纠错 v2（取景契约 + 双视角分工 + 轮次化拍摄）

| 项目 | 内容 |
|---|---|
| 状态 | 方案已与用户逐条确认，待实现 |
| 日期 | 2026-11-19 |
| 前置 | `handoffs/2026-11-19-M5-video.md`（M5 实现与实测）、`content/video_checks.yaml` v1.3 |
| 演示 | 2026-11-21，只实机跑侧拍；俯拍只讲方案 |

## 一、问题与根因

M5 的实拍结论：侧面拍摄姿态可用，俯拍整段判为看不清，中文口令识别不稳。

根因不是模型精度，是判据本身是侧面几何。`pawcoach/pose/rules.py` 用
`h = (tail_base_y - neck_base_y) / 体长` 判坐，只有侧视时这个比值才对应"臀部落地"。
俯视时左右对称关键点横向拉开，`max_width_ratio = 0.4` 直接判成正面/背面并返回 unclear。
**俯拍是设计上主动放弃的，不是算不准。**

第二个事实：现有 8 个检测器里只有 4 个真正需要姿态（奖励太晚、起身后才给奖励、
狗自己结束等待、长等待没有保持费）。其余 4 个（口令重复、一次练太久、目标时长太长、
失败时出声纠正）依赖音频与时长，与视角无关。

## 二、已确认的产品决策

| 议题 | 决定 |
|---|---|
| 视角 | 侧拍与俯拍都要支持 |
| 画面内容 | 必须看到主人的手和狗 |
| 数据 | 赛后自采 30–50 段真实视频，自己和朋友的狗 |
| 教学闭环 | 看时间线对比，然后重拍一次 |
| 录制形态 | 轮次化引导录制，不再随手录一整段 |
| 反馈时机 | 录完一组统一看，不做录制中判定 |
| 机位分工 | 侧拍判姿态与时机，俯拍判手法与空间关系 |
| 视频留存 | 默认留存，用户可申请删除 |

## 三、总体设计

```
选择机位（侧拍 / 俯拍，或由传感器推荐）
  → 取景自检（传感器 + 检测框 + 关键点/掩膜可见度 + 亮度 + 模糊）
      红灯：说明原因，不允许开录
      绿灯：倒计时 5 秒
  → 轮次化录制：说口令 → 狗响应 → 标记 → 奖励，每轮 ≤15 秒，每组 3–5 轮
  → 整组上传，一次判定（轮次级错误 + 时间线）
  → 时间线对比页：四条轨道 + 标准时间线 + 一条改进点
  → 重拍：只重录不合格的轮次，两次时间线并排
  → 结果入库，按留存设置决定原始视频去留
```

## 四、拍摄契约

录制前实时自检，不合格不进录制。把"识别率"问题换成人人都能过的"取景合格率"。

| 项 | 侧拍模式 | 俯拍模式 |
|---|---|---|
| 手机姿态 | 横放靠墙或支架，俯仰角 0° ±10°（读加速度计） | 竖持胸前高度，俯仰角 30°–60° |
| 距离 | 距狗 2–2.5 米 | 距狗 1–1.5 米 |
| 狗在画面 | 占画面宽度 30%–60%，侧身（复用对称关键点宽度比 < 0.4） | 完整在框内，正对镜头前方 |
| 主人 | 至少手和上身在画面内 | 手自然入画 |
| 尺度参照 | 狗体长 | 地面纹理或训练垫 |
| 实时检测项 | 狗检测框完整、关键点可见比例 ≥ 28/39、亮度、拉普拉斯方差 | 狗分割掩膜面积稳定、手部入画、亮度、模糊 |

判定分三档：绿（可录）、黄（能录但质量下降，会提示可能判不准）、红（不可录，一句话说清原因，
例如"手机要横过来"、"退后半米，狗太小"、"画面太暗"）。

## 五、轮次化录制

- 一轮 = 一个完整回合：口令 → 狗响应 → 标记 → 奖励。上限 15 秒。
- 静默超过 3 秒自动切下一轮；也可手动点"这一轮结束"。
- 每组 3–5 轮，与 `video_checks.yaml` 的 `min_reliable_trials` 对齐（多数检测器为 2）。
- 单轮不合格只重录该轮，不重录整组。这是"重拍一次"能落地的前提。

理由：长视频一次性对齐的错误会直接变成误判；轮次化后每轮独立、短、模板一致，
对齐和切分的可靠性都上一个台阶，教学节奏也更清楚，还天然产出同一只狗的正误对照数据。

## 六、双视角判据

### 侧拍（复用现有，已验证）

`h = (tail_base_y - neck_base_y) / 体长` 判坐/站，接现有的 8 个检测器里需要姿态的 4 个。
不改模型，只改输入（取景契约 + 轮次切分）。

### 俯拍（新增，赛后）

- 用 YOLOv8-seg 狗实例分割代替关键点，俯视下不再依赖左右对称关键点。
- 俯视判据（都是可测的几何量）：
  - 脊柱投影长度：沿狗朝向的掩膜长度，坐下时从水平转向竖直，投影缩短两三成。
  - 后躯圆度：后端宽度 / 体长，坐下时明显变大。
  - 头相对前爪的位置：坐下时头落在前爪上方。
  - 掩膜面积变化：俯视投影面积的时序变化。
- 分类器：8–12 维时序特征 + 3 秒滑动窗口，输出 sit / stand / down / unclear。
  先做规则基线（阈值来自自采数据），确认有效再上小模型。
- 俯拍独有、侧拍做不到的手法判据：
  - 奖励落点与狗嘴的距离（递得太远 / 举得太高）。
  - 手是否越过狗头顶（按压、推倒）。
  - 手的运动速度与幅度（手势过大、抢狗的动作）。

### 明确不做

- 不追求"任意角度都能识别"。取景契约就是产品的边界。
- 不在两天内做俯视识别，只在 UI 与数据层预留 `view` 字段。

## 七、音频：优先级高于姿态

口令和标记词是视角无关的信号，也是当前真瓶颈：实拍里"坐"被 Whisper 听成"走"，
英文 "sit" 被听成 "that's"。

- 限定词表的关键词检测：只认这只狗口令表里的词 + 标记词 + 释放词 + 纠正词。
- 响片与拍手用瞬态检测（能量包络 + 模板），比整段转写稳得多。
- Whisper 降级为兜底，不进实时路径。
- 识别不到时明确说"这一轮没听到口令"，不静默出错。

## 八、教学产物：时间线对比

- 四条轨道：主人口令、狗的姿态、标记词、奖励。
- 标准时间线来自内容库 `success_criteria` 的量化部分，叠在上方。
- 偏差高亮，例如"第 2 秒坐下，第 4.3 秒才奖励，晚了 2.3 秒"。
- 结论区只放内容库原文 + 一条"下次改这一点"。
- 底部"重拍一次"，重拍后两次时间线并排比较。

## 九、数据与隐私

- 赛后采集 30–50 段：坐 / 短等待 / 长等待 × 正误 × 侧拍俯拍 × 不同品种、光线、地面。
- 标注到轮次级：sit onset、marker、reward、错误类型。可用现有 align 结果做半自动预标注。
- 默认留存（用户已确认）。App 内必须做到：
  - 首次上传时明确告知留存范围（分析结果与特征；原始视频按声明期限）。
  - "我的"里提供删除入口，删除后联动服务端清理。
- 留存的是特征与时间线，原始视频不是默认长期保存项。

## 十、21 日演示（侧拍）

1. 摆位：找一面墙，手机横放靠墙，2 米外放训练垫，主人入画。
2. 脚本：故意做一次"奖励晚 2 秒"，现场判定 → 时间线高亮 → 按提示重拍 → 两次对比。
3. 兜底：预录两段同场景视频，服务不响应时切预录，不现场调试。
4. 俯拍：只讲取景标准和分工，不承诺现场识别。

## 十一、风险

| 风险 | 应对 |
|---|---|
| 俯拍数据不足 | 先做规则基线，不追 ML；数据不够就不发版 |
| "必须看到手"与侧拍 2 米在小户型冲突 | 手法教学默认推荐俯拍，侧拍只做姿态与时机 |
| 默认留存引发隐私质疑 | 首传告知 + 设置内可删 + 只留特征 |
| 轮次化录制增加操作步骤 | 演示控制在 3 轮内完成，界面只留一个按钮 |
| 取景自检误报 | 红灯必须给具体原因和一句怎么改，允许"仍然录制" |

## 十二、验收

- 侧拍：三种错误各 3 段视频，召回 ≥ 2/3，误报 ≤ 1。
- 取景：10 次摆位，至少 8 次一次通过自检。
- 时间线：主人能在不看解释的情况下指出自己错在哪一步（现场找 2 人试）。
- 俯拍：本阶段只验收取景引导与数据采集流程，识别另立里程碑。

## 实现状态（2026-11-20）

本节记录已经做出来并验证过的部分，以及没做的部分。以上各节是方案，本节才是现状。

### 已做

| 项 | 内容 |
|---|---|
| 取景自检服务 | `video_service/pawcoach/framing.py` 与 `POST /frame-check`。单帧 YOLO 找狗和人，按机位的取景契约判红 / 黄 / 绿，返回一句改进提示与归一化的框。同一时刻只跑一帧，忙时 429，缺检测器时 503，不落盘 |
| 引导拍摄页 | `app/lib/features/video/guided_capture_page.dart`。相机预览、引导框、实时红黄绿、倒计时 3 秒、录制、结束后走原有的上传分析。入口是视频纠错页第一个按钮 |
| 降级 | 连续 3 次连不上或缺检测器，框变成虚线静态框，提示"取景检查不可用"，仍可录制。服务忙只丢帧。成功一次自动恢复 |
| 帧转换 | 相机原始帧转正、缩到长边 320 再上传。Android 的 YUV 与 NV21、iOS 的 BGRA 都有，未做 JPEG 编码 |
| 权限 | Android 加了相机与麦克风权限。iOS 的说明文案工作区里原本就有 |

### 验证过什么

- 服务端 164 项通过，其中取景相关 34 项。App 全量 691 项通过，取景相关 60 项左右。
- 红灯规则做过变异检查：把"红灯提示仍然录制"改坏，对应测试会失败，还原后通过。
- 用两段真实视频回放：侧拍一段 112 帧、俯拍一段 35 帧，经 HTTP 发给服务，零失败。本机往返耗时中位 14 毫秒。
- Android 模拟器：预览出画面、取景请求持续发出、红灯与"仍然录制"按钮、倒计时、录制计时、结束后自动上传并进入分析，整条链路通。服务端分析后目录里没有残留。

### 没验证、没做

- **没有真机验证。** 模拟器的相机是虚拟场景，里面没有狗，所以只验证了链路，没有验证真实相机帧下狗能不能亮绿。真实狗的判断只来自两段回放视频。
- **阈值只来自两段视频。** 回放里侧拍约四成帧是绿，俯拍约三成。红灯几乎都是"狗被画面边缘截断"。
- **截断判断有误报，原因不是余量设得不对。** 判定只看狗框边缘离画面边缘的距离，余量 1% 在 320 像素的帧上只有约 2 个像素。侧拍片段 39 个截断帧里，只有 6 帧狗框恰好贴边，其余 33 帧离边缘不到 1%。看图确认：10.5 秒狗确实有一部分在画面外，是真截断；20 秒和 42 到 49 秒狗完整坐在画面左缘，没有被截断，也被判了红。
- **调余量解决不了。** 真截断帧的距离约 0.34% 到 0.37%，完整入画的误报帧约 0.4% 到 1%，两组重叠。余量降到 0.5% 仍有 16 帧判截断，降到 0.3% 虽然只剩 7 帧，但 10.5 秒那种真截断也漏掉了。所以没有改阈值。要分开这两种情况，需要比"离边缘多近"更多的信息，这要靠更多真实素材来定。
- **对演示的影响：** 红灯不阻止录制，只是按钮变成"仍然录制"并显示截断提示。狗离画面边缘近时会看到这个误报，演示时让狗站在引导框中间，不要贴着画面边缘。
- **模拟器上没有测到绿灯。** 绿灯只在回放和单测里出现过。
- **没做：** 多轮录制与只重拍某一轮、时间线对比页、留存与删除入口、音频关键词检测、俯拍识别、手的位置检测。俯拍现在只有取景框，没有判定。
- **iOS 没跑。** 只写了 BGRA 的转换与单测，没有在 iOS 设备或模拟器上试过。

### 演示前要做

1. 真机上走一遍：笔记本连现场 Wi-Fi，手机"我的 → 服务器地址"填笔记本地址。取景自检与视频分析共用同一个服务，但视频分析的地址来自构建参数，需要和服务器地址一致。
2. 用真狗在目标场地拍一次，看绿灯能不能亮。狗要站在画面中间，不要贴边，否则会碰到上面说的截断误报。
3. 预录两段兜底视频，服务不通时直接用相册选择。
